How to scan

Enter a hostname or URL and click Analyze. The scanner does a passive GET plus DNS, WHOIS, and TLS from this host. It does not probe or exploit the target.

  • Site — the name browsers will use (Host header and TLS SNI), for example checkpoint.com.
  • Pre-cutover connect via — optional. Same idea as a hosts-file entry or curl --connect-to: TCP goes to that CNAME/IP (usually the Check Point ….i2.checkpoint.com name) while Host/TLS stay on the site. Use this before the customer changes public DNS. The via name must resolve to a public IP.
  • Timing is from this scanner, not end users. Save a baseline, scan again later, and Compare for a Check Point / CNAME / IP / header / TTFB diff.
  • For browser-path questions (cache, 403/429, login, p95), capture a HAR and open WAFBuddy.

How to read a report

  • Performance — DNS, Connect+TLS, TTFB, and redirects, graded good / ok / slow for this scanner. Treat TTFB deltas under ~50 ms or ~15% as noise.
  • DNS / IP — public records. With connect-via, these still show the current origin; HTTP/TLS in the scan used the via path.
  • CDN / WAF / load balancer — vendor plus why this scan matched (header, CNAME, or IP org). Cloudflare CDN vs WAF share CF-RAY. Check Point WAF is confirmed by i2.checkpoint.com.
  • SSL / security headers — certificate and live response headers. Missing HSTS/CSP/etc. show up here.
  • Copy markdown is for tickets. Optional ticket/customer/notes stay in this browser only.
